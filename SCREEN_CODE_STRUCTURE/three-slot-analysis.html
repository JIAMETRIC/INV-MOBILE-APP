Verdict

sound

Your method is sound. It's the structure that React Native's flexbox, Material Design 3, Apple's HIG and this project's own design kit all already assume, so it adds no new mechanism and breaks no rule. Its real costs are three couplings it creates, each with a known fix the scaffold can own once:

1footer height ↔ Main's bottom padding
2keyboard ↔ footer
3number of columns ↔ screen width

The one place it bends: on wide screens "footer" stops being a global bar and becomes a per-pane action row. Material says the same, so that's a rule to write down, not a flaw.

Your pitfalls table, re-checked

All four rows hold. Two refinements: "forgetting flex: 1" makes the footer sit right under the last row (and tall content pushes it off-screen); and the footer rises with the keyboard because Android adjustResize shrinks the window and the column reflows, not because of the flex column alone.

The six conventions

1
Headerfixed, pads the status inset, title marked as a heading.
2
Mainone scroller; sides 20, gap 16; bottom padding = nav + footer (+ FAB).
3
Footercompact widths only; in the flex column; pads the gesture inset.
4
Rows / columnsgap: 12, equal columns flex: 1, ≤ 3 on phones, cells ≥ 44, each split row says when it stacks.
5
Listsmemoised rows; the last row clears footer and nav.
6
Navigationnav and rail belong to the shell, never to a screen.
